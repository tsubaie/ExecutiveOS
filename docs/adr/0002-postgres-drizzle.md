# ADR 0002 — PostgreSQL with Drizzle ORM and generated migrations

**Status:** accepted (2026-09-07); amended by `03-data-model.md` § Migration rules on 2026-09-07: reviewed custom SQL migrations (triggers, generated columns, partial and trigram indexes, deferrable constraints) are allowed, and the runner applies migrations once under an advisory lock. The body below is unchanged.

## Context

The predecessor had no migration system: two drifting migration folders, a `schema.sql` that could not build the database, and tables whose real shape existed only in production. Inline SQL was copy-pasted across 78 route files. A rewrite must make the database rebuildable from the repo and keep SQL in one layer.

## Decision

PostgreSQL 16 is the only database. Schema is declared in TypeScript with Drizzle (`modules/*/schema.ts`), migrations are generated by `drizzle-kit` and committed under `drizzle/`, applied on container start, and checked by `audit:schema`. All queries use Drizzle's builder inside `repo.ts`. UUID v7 primary keys generated in the app. Soft delete and standard audit columns on every user-facing table.

## Consequences

- One source of truth for schema; types flow from it.
- Hand-written SQL is limited to expressions Drizzle cannot express.
- Postgres enum types are avoided (CHECK constraints instead) to keep migrations simple.
- No down migrations: restore from backup is the rollback path, so backups are a v1 feature.

## Alternatives considered

- **Prisma**: mature, but a heavier runtime, its own query language, and slower cold starts in containers.
- **Kysely + dbmate**: excellent typed SQL, but schema and migrations would be two artifacts to keep in sync.
- **Raw `pg`**: what the predecessor did; rejected for the reasons in Context.
- **SQLite**: attractive for single-user self-hosting, but multi-user writes, `SKIP LOCKED` job claims, and array columns push toward Postgres.
